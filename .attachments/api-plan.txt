Proposed direction 
We should evolve PackProof into a unified, API-first evidence platform organized around a canonical

The PayPal-button analogy is useful for integration simplicity, but PackProof should not imitate PayPalâ€™s payment semantics. The PackProof button should behave like this: 
The merchant installs a PackProof app, plugin, extension, or JavaScript component. 
The integration supplies structured listing, product, variant, cart, or order data to PackProof. 
PackProof creates an immutable, provenance-bearing commerce-context snapshot. 
The button receives only a short-lived handoff tokenâ€”never the merchantâ€™s private API credential. 
Clicking the button opens a hosted or native PackProof flow. 
The passport form is already populated with the item description, identifiers, selected variant, price, currency, product URL, and other available information. 
The user reviews and confirms the imported information instead of retyping it. 
Once an actual order exists, the merchantâ€™s server binds the passport to the authoritative order and line item. 
PackProof capture, evidence, return, notification, reporting, and webhook components all operate on that same canonical record. 
The critical architectural principle is: 
PackProof elements should interoperate through shared domain services, stable resource contracts, and versioned eventsâ€”not by allowing every component to call every other component or write directly to Firestore. 
That gives us seamless interoperability without creating an unmaintainable web of dependencies. 
The existing master plan already calls for shared domain services, a stable API, webhooks, SDKs, and commerce integrations. The important sequencing change is that the  
commerce-context model must be established near the beginning

The commerce-context model 
The imported product/listing information should not be inserted directly into the transaction as an undifferentiated description. It needs a first-class provenance model.

Three PackProof button modes 
A single integration component can support three modes, but they must have different evidentiary meaning. 
1. Listing mode 
Placement: 
Product page. 
Marketplace listing. 
Merchant catalog page. 
Behavior: 
Imports product/listing data. 
Creates a prefilled passport draft. 
Does not claim an order or purchase exists. 
Does not assume a buyer identity. 
Can allow a user to begin or save a PackProof intent. 
Trust level: 
PLATFORM_API_ATTESTED 
 when obtained through a server/platform API. 
PAGE_DECLARED 
 when obtained only from page JSON-LD or JavaScript configuration. 
2. Checkout mode 
Placement: 
Cart. 
Checkout extension. 
Checkout-review screen. 
Behavior: 
Imports selected variant, quantity, amount, and seller context. 
Creates or updates a checkout-bound PackProof intent. 
Can associate the eventual order through a checkout completion callback. 
Still does not treat browser-provided payment state as authoritative. 
3. Order mode 
Placement: 
Order confirmation. 
Merchant administration. 
Marketplace seller workflow. 
Fulfillment workflow. 
Behavior: 
Merchant server supplies the authoritative order and line-item identifiers. 
Creates or binds the PackProof transaction. 
Issues seller/buyer claim or capture invitations. 
Starts the normal evidence and shipment lifecycle. 
Produces final status and webhook events back to the commerce system. 
This should become the strongest and preferred integration mode because the merchant serverâ€”not the browserâ€”confirms that the order exists.
